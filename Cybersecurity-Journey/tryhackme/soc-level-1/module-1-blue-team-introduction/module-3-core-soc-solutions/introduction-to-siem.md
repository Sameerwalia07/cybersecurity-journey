## 🧠 In My Own Words

### Log Source Categories, With Examples

**Host-centric logs** — generated by activity on/related to a specific
host (Windows, Linux, servers):
- A user accessing a file
- A user attempting to authenticate
- Process execution
- A process adding/editing/deleting a registry key
- PowerShell execution

**Network-centric logs** — generated when hosts communicate with each
other or the internet (firewalls, IDS/IPS, routers):
- SSH connections
- FTP file access
- Web traffic
- VPN access to company resources
- Network file sharing activity

### A Worked Correlation Example

Individually, none of these look suspicious:
1. Haris logs in via VPN from an IP he's never used before
2. Haris accesses documents on a shared drive
3. Haris executes a PowerShell script
4. The system makes an outbound network connection

But **correlated together** by a SIEM within a 5-minute window, this
pattern could point to **data exfiltration via a compromised VPN
credential** — exactly the kind of story a single log alone could never
tell.

### Log Sources in Practice

- **Windows** — every event is logged and viewable via **Event Viewer**,
  each event type assigned a unique **Event ID**, then forwarded to the
  SIEM
- **Linux** — key log locations: `/var/log/httpd` (HTTP requests/errors),
  `/var/log/cron` (scheduled jobs), `/var/log/auth.log` /
  `/var/log/secure` (authentication), `/var/log/kern` (kernel events)
- **Web Server** — monitoring inbound/outbound requests is critical for
  catching web attacks; Apache logs commonly sit at `/var/log/apache` or
  `/var/log/httpd`

### Log Ingestion Methods

1. **Agent/Forwarder** — a lightweight tool installed on the endpoint that
   captures and sends logs to the SIEM (e.g. Splunk's "forwarder")
2. **Syslog** — a widely used protocol for collecting and sending real-time
   log data from systems like web servers and databases
3. **Manual Upload** — some SIEMs (Splunk, ELK) allow direct upload of
   offline data for quick ad-hoc analysis
4. **Port Forwarding** — the SIEM listens on a configured port, and
   endpoints forward data directly to that port

### How a Detection Rule Actually Gets Built

Detection rules are essentially **logical expressions** that trigger when
specific conditions are met.

**Use Case 1 — Detecting log clearing (anti-forensics):**
Adversaries often clear event logs post-exploitation to cover their tracks.
Windows logs a unique **Event ID 104** whenever logs are cleared.
> **Rule:** If Log Source = WinEventLog AND EventID = 104 →
> Trigger alert `"Event Log Cleared"`

**Use Case 2 — Detecting recon commands (`whoami`):**
Adversaries commonly run `whoami` after exploitation/privilege escalation.
Building this rule requires identifying the right fields:
- **Log source:** where the event is captured
- **Event ID:** `4688` (Process Execution)
- **NewProcessName:** the specific field to check for `whoami`

> **Rule:** If Log Source = WinEventLog AND EventCode = 4688 AND
> NewProcessName contains `whoami` →
> Trigger alert `"WHOAMI command Execution DETECTED"`

Seeing these two examples side by side made it click for me: a rule is
really just "which log source + which specific field/value combination +
what to call the alert."

### Alert Investigation — What Happens Next

Analysts spend much of their SIEM time in **dashboards**, which summarise
key network details (alert highlights, failed logins, events ingested,
rules triggered, top domains visited, etc.). Once an alert triggers, the
analyst examines the associated events, checks which rule conditions were
met, and determines a verdict. Depending on the outcome:
- **False Positive** → may require **tuning the rule** to prevent repeat
  false alarms
- **True Positive** → proceed to deeper investigation
- **Contact the asset owner** to ask about the activity directly
- **Isolate the infected host** if suspicious activity is confirmed
- **Block the suspicious IP**
